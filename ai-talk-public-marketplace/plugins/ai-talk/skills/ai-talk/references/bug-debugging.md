# Bug 定位

把问题现象、排查边界、证据要求和验证方式说清楚。不要把猜测写成根因，也不要替 Plan 模式展开实施步骤。

## 必须补充

- 实际现象、预期结果、影响和已知触发条件；未知内容明确标记。
- 用户提到的环境、日志、请求、最近变更和相关代码范围。
- 与现象直接相关的生命周期、状态更新、定时器、事件、请求、异步时序或缓存范围。
- 能够证明或排除原因的代码位置、日志、请求、断点或最小实验。
- 修复前后的复现或回归验证方式。

“帮我看看”“排查”“先定位”默认识别为只分析，必须写明“本轮只分析和定位，不修改代码”。缺少日志时可以先生成定位话术，不机械阻塞。

## 紧凑话术骨架

```text
# 任务话术

请定位【功能】出现的【实际现象】，预期为【预期结果】。

本轮只分析和定位，不修改代码。范围限定为【相关页面/模块】及直接依赖，重点检查生命周期、状态更新、定时器和异步时序。区分事实、推测、已排除和未确认原因，结论需附代码位置、日志、请求、断点或最小实验等证据。

请输出调用链、根因及依据、影响范围、最小处理建议和验证方式；没有足够证据时明确下一步取证方法。
```
