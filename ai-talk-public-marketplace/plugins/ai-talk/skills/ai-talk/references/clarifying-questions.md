# 智能追问与默认规则

追问的目的只是避免 AI 在关键方向上猜测，不是让用户填写需求表单。

## 信息分类

- `直接证据`：用户明确说出或确认的信息、附件直接可见内容、已读取目标文件的真实结构，以及 Skill-only 索引返回的路由事实。
- `AI 语义判断`：由直接证据支持的归纳、合并、改写和对应结论；必须说明依据，不得冒充用户原话或项目事实。
- `建议（非需求）`：尚未得到用户确认的可选产品或技术建议；不得转化为必须实现项。
- `待确认信息`：证据不足或存在多个合理解释的信息。非阻塞项可以保留，只有会改变目标、权限、范围或关键结果时才追问。

不要生成无依据的 Assumption。允许主动整理证据之间的关系，但不能用“通常如此”代替证据。

## 何时追问

只有答案不同会改变以下内容时才追问：

- 对任务目标或问题现象的理解
- analyze、plan、modify_and_verify 或 review 的期望处理方式
- 允许修改的代码范围
- 关键业务结果或兼容边界
- 最终验收方式

默认只问一个最影响方向的问题。只有多个相互独立的答案都会改变目标、权限或验收时，才允许一轮询问两到三个问题；每轮绝不超过三个。场景已经明确时不要再问用户选择模板。

## 只基于输入提问

AI Talk 可以有界读取用户明确附带或指定的目标文件，但不读取 `AGENTS.md`、`README.md`、`package.json`、目录结构、Git 状态、同目录文件、imports、组件依赖或工具函数。结合当前对话与已读取目标文件判断是否存在会改变提示词方向的阻塞项。

目标文件以外、能够由后续 Codex 从项目读取的信息，不向用户追问，也不在 AI Talk 当前轮读取；直接写成后续执行步骤。不得把未读取信息写成项目事实。

## 提问方式

- 每题只问一个会影响方向的决策点，并结合用户当前任务具体表述。
- 能列出主要方向时，提供 2–3 个互斥选项和一句影响说明；环境支持结构化输入工具时可优先使用。
- 无法枚举的复现步骤、文案或业务规则，用一个自然语言问题询问，不为凑选项编造答案。
- 说明用户可以暂不回答；未回答时保持为未知，不选择产品或技术默认值。
- 用户说“先生成”“按默认处理”或拒绝回答时，立即停止追问。

正确示例：

```text
还缺少一个会影响定位方向的信息：

这个问题通常发生在首次进入页面、返回页面，还是连续操作以后？

如果暂时不清楚，我会把触发条件保留为未确认，不把任何常见场景写成事实。
```

避免：

```text
请填写技术栈、项目名称、文件路径、启动命令、测试命令和完整验收标准。
```

## 默认处理

- 期望处理方式不明确：默认 `modify_and_verify`。用户陈述“需要某能力”或期望结果时，视为要求后续 Codex 直接实现并验证。
- 只有用户明确要求“先给方案”“讨论方案”或等价表达时使用 `plan`。
- 修改范围不明确：限定为用户提到的页面、模块及其直接依赖，不授权无关重构。
- 验收方式不明确：不生成验收标准；只要求后续 Codex 报告实际执行的验证。
- 资料缺失但不影响任务方向：直接生成最小话术；存在真实歧义时可列为待确认，但不阻塞输出。
- 多种解释都会造成明显不同结果：只问最关键的一个问题，不自行选择高风险方向。

项目中可读取的数据源、调用方式、组件 API 和实现细节不是用户必须先确认的产品决策。将它们写成后续 Codex 的读取与实施步骤，不要因此把执行任务降级为方案任务。

## 场景提示

- Bug：优先确认实际现象、触发条件和预期结果；后续是否修改由期望处理方式表达，但所有话术仍需审查。
- 新需求：基于用户明确结果、交互和附件建立语义对应；可以归纳任务目标，但不得补造产品行为。只使用 frontmatter 路由事实，不读取项目事实。
- UI：优先识别截图或设计稿中任务相关的模块、状态和位置，把它们对应到用户需求；不要询问资料中已经可见的信息，也不要抄录全部图片文字。
- 接口：优先确认权威契约和联调目标；没有契约时要求收集真实请求/响应，不编造字段。
- 审查：优先确认审查范围；默认只审查不修改。
- 清理：优先确认行为兼容边界和范围；无法证明安全的删除只报告。
- 测试：优先确认要保护的行为或回归；测试框架和命令从项目读取。
- 方案讨论：优先确认决策目标和硬约束；不提前拆成实施任务。
