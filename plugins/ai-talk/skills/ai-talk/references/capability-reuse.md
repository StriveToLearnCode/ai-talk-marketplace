# 能力发现与复用

在生成任务摘要或任务话术前，先发现与当前任务相关的已有能力。目标是组合真实存在且适用的能力，不是展示完整目录，也不是为凑数量强行匹配。

## 统一上下文入口

在可访问项目时只运行一次统一上下文命令：

```bash
python3 <AI Talk Skill 目录>/scripts/collect_context.py \
  --root <项目根目录> \
  --query '<用户原始需求与已确认补充>'
```

`collect_context.py` 内部调用 `build-capability-index.mjs`，把基础项目上下文与能力候选合并到同一个 `task_context`。正常 AI Talk 流程不要分别运行两个脚本，也不要让模型自行拼接两份输出。Node 脚本只保留为内部索引引擎和独立调试入口。

脚本默认发现：

- 项目中的 `SKILL.md`、Prompt、AGENTS/README/配置规范、templates。
- `components`、`composables`、`hooks`、`utils` 中的可复用实现。
- `pages`、`views`、`examples`、`stories`、`legacy`、`archive` 中的同类实现。
- 常见用户 Skill 根目录和已安装 Codex 插件中的 Skill。

公司或团队目录不固定。已知目录时在统一命令上使用可重复的 `--source-root company-name=/absolute/path`；也可用系统路径分隔符连接多个 `AI_TALK_CAPABILITY_ROOTS` 条目。目录不存在时跳过并保留 warning，不编造来源。

## 选择能力

1. 使用 `task_context.capabilities.selected` 中的第一项作为主能力候选，最多使用后两项作为辅助能力候选。
2. 读取每个候选的真实文件，确认描述、适用条件、调用方法、依赖和限制。组件或工具还要按需读取一个真实消费者、测试或同类页面。
3. 主能力负责当前任务的主要工作流。辅助能力只补足验证、浏览器操作、接口契约、组件复用等明确缺口，不得覆盖主能力的约束。
4. 项目和公司能力通常比通用能力更贴近当前代码，但相关性和适用条件优先于来源层级。
5. 多个能力冲突时，遵守系统/开发者指令、项目 `AGENTS.md` 和用户当前要求；不能兼容的候选不进入最终组合。
6. 没有足够相关的候选时允许不选择能力。不要把 AI Talk 自身作为待复用能力，不要因为名称相似就声称能力可用。

## 写入当前任务

只写入已经复核的能力：

- `主能力`：名称、来源和它负责的工作流。
- `辅助能力`：最多两个，分别说明补足的环节。
- `复用对象`：需要优先使用的组件、函数、Prompt、规范或同类实现路径。
- `复用约束`：先沿用现有 API、状态模型、样式和测试方式；只有确认现有能力不适用时才新增实现，并说明原因。

默认确认摘要增加一行“能力复用”。显式话术输出时，把上述内容压缩进“执行要求”或“相关范围”，不要附完整索引、评分或扫描日志。

## 降级与边界

- 统一脚本不可用，或 `task_context.capabilities.status` 为 `unavailable` 时，按同样顺序使用 `rg --files` 和定向搜索，只检查与任务直接相关的目录。
- 索引只提供候选，不能替代读取文件和运行验证。
- 不读取 `.env`、密钥、令牌、用户隐私、依赖目录、构建产物或超大文件。
- 不自动安装、修改或调用未授权的外部能力。Skill 的存在不代表本轮可以绕过当前模式、沙箱或用户授权。
- 不为了能力发现扫描无关的大型代码区；命中范围过宽时，先用任务模块、业务名或用户提到的文件缩小查询。
