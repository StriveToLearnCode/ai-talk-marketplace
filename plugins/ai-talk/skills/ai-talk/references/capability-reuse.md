# 能力发现与复用

AI Talk 使用两层能力发现：先实际调用当前会话可用的专用 Skill，再用一次项目本地索引补充规则、组件、utility、Prompt 和历史实现。Skill 元数据匹配不等于 Skill 已经被调用。组件开发需求必须先完成公司组件检索决策，不能把公司和项目候选合并展示。

## 1. 原生 Skill 调用

当前 Codex 会话公开的 Available Skills 是权威 Skill 目录。

1. 根据 `name` 和 `description` 的完整语义选择最小适用集合。
2. 专用组件目录、物料平台、历史实现、接口契约或活动开发 Skill 优先于通用前端、教学或调试 Skill。
3. 完整读取命中 Skill 的 `SKILL.md` 和其要求的必要 reference。
4. 执行该 Skill 与当前任务相关的只读检索步骤，并记录真实工具结果。
5. 跳过修改文件、构建、部署、提交和外部写入动作。

不得因为查询中包含“开发”“组件”“验证”等常见词就选择通用 Skill。无法说明该 Skill 如何提供当前任务需要的专门能力时，不调用它。

### 公司组件检索

1. 从用户原话和真实项目文件提取有来源、直接相关的约束，再调用语义明确覆盖公司封装组件检索的 Skill。
2. 查询只包含用户明确需求、已验证项目约束，以及用户明确给出的目标场景、交互和状态；不得用常见组件形态补全查询。用户没有明确组件名时，不得加入任何猜测名称。
3. 只保留具有真实路径或稳定标识、实际匹配证据且不是 `low_relevance` 的结果。
4. 唯一明显最佳且证据充分的结果可直接采用；缺少关键证据、结果接近或适用边界不清楚时，最多展示三个候选并等待用户选择。
5. 候选展示严格使用以下格式，不附加路径、复用方式、适配项或兼容性结论：

```text
1. 组件名称：<真实名称>
   匹配原因：<基于实际 Skill 结果的简短原因>
```

6. 用户选择后，最终话术才写入所选组件的真实路径或标识、来源 Skill 和与用户需求直接相关的匹配证据。组件其余能力不得进入需求；未选择的组件不得成为实现依赖。

推荐确定性和执行兼容性必须分开。直接采用只表示推荐方向明确，`execution_validation` 仍为 `null`。

## 2. 项目本地索引

每轮只运行一次：

```bash
python3 <AI Talk Skill 目录>/scripts/collect_context.py \
  --root <项目根目录> \
  --query '<用户需求与已确认补充>'
```

组件开发的公司检索阶段增加：

```bash
--defer-project-component-choice
```

此时 `task_context.capabilities.project_component_selection_deferred` 为 `true`。项目内 `component` 和 `implementation` 仍可存在于完整索引结果中，但不出现在 `task_context` 的自动项或待选项中，也不改变 `prompt_state`。只有用户选择“检查当前项目已有实现”后，才在下一轮取消该参数并启用本地组件选择。

用户给出项目内路径时增加 `--related`；明确知道公司或团队能力目录时增加 `--source-root label=/absolute/path`。不要猜测公司目录。

索引只扫描项目根目录和显式 `--source-root`。它不扫描 `~/.codex/skills`、`~/.cc-switch/skills`、插件缓存或其他用户 Skill 目录，这些来源由当前会话的 Available Skills 负责。

## 3. 结果合并

实际调用 Skill 的结果优先于本地关键词索引。合并时保留：

- 名称、类型、来源和真实路径或标识。
- Skill 名称、实际查询动作和返回证据。
- `candidate_reuse`、`candidate_reference` 或 `low_relevance`。
- 只有与用户明确需求直接相关、真实接入时才需要后续 Codex 验证的内容；不得固定罗列完整组件 API。
- 强行复用、公共组件改动或依赖不兼容风险。

索引返回的 `skill_candidates` 只用于发现项目或显式目录中的 Skill。AI Talk 必须重新判断语义适用性、完整读取并实际调用，才能把它列入“实际调用 Skill”。

公司组件流程是例外：公司检索得到明确结果前，项目组件不得与其合并、补位或参与排序。项目规则、技术栈和非组件约束仍可写入最终话术。

## 4. 项目候选

用户明确选择“检查当前项目已有实现”后，唯一且高相关的项目内组件可自动使用 `prefer_reuse`，唯一相关历史实现可自动使用 `prefer_reference`。

以下情况才要求用户选择：

- 多个高相关实现竞争同一职责。
- 共享或跨项目组件的适配方式不明确。
- 无法判断应复用还是仅参考。

项目组件候选同样最多展示三个。组件选择界面只显示组件名称和匹配原因；非组件能力可继续显示必要路径与差异。宿主支持结构化输入时使用真实选择控件，否则显示编号并等待自然语言选择。不得输出确认、取消或点击式伪按钮。

## 5. 失败与空结果

- 公司组件检索 Skill 不存在、读取或调用失败、返回空结果或只有低相关结果：显示“未找到合适的公司封装组件”，保留具体原因，并提供“检查当前项目已有实现”或“新建本地组件”。不得自动展示项目组件。
- 用户拒绝全部公司候选：按公司组件无结果处理，进入同一降级选择。
- 本地索引失败：说明检查失败的范围，最终话术要求后续 Codex 重新检查目标目录和同类实现。

`execution_validation` 在 AI Talk 阶段始终为 `null`。用户选择也不能升级为兼容性结论。
