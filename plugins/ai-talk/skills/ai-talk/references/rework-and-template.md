# 返工话术与模板沉淀

## 返工话术

用户说“还是不行”“没有生效”“问题还在”“上次改错了”“重新看看”“继续排查”时，优先使用当前对话中的上一轮任务、判断、改动和结果，不要求用户重新描述完整背景。

只写当前对话中有依据的内容。上一轮信息缺失时，用“未获取到”标记，并最多询问一个会改变重新定位方向的问题，例如当前仍存在的具体现象。不要编造上一轮根因或修改。

```text
# 返工话术

## 上一轮判断
【有依据的上一轮原因；没有则标记未获取到】

## 上一轮处理
【有依据的改动、方案或验证；没有则标记未获取到】

## 当前结果
【问题仍然存在的表现，以及与上一轮相比是否有变化】

## 本轮目标
先重新定位，再决定是否继续修改。不要直接重复上一轮没有证据的判断。

## 本轮要求
- 检查上一轮修改是否真正生效，当前运行环境是否使用最新代码。
- 检查构建、缓存、部署、分支或启动进程是否让旧代码仍在运行。
- 重新收集代码、日志、请求、断点或可复现操作等运行证据。
- 区分已经排除、仍可能存在和尚未确认的原因。
- 新结论需要解释为什么能够覆盖当前现象。
- 修改前先说明新的依据和最小处理方案；除非用户明确允许直接执行。

## 输出要求
请输出上一轮已验证内容、当前新增证据、重新定位结论、下一步建议和仍未确认的信息。
```

返工不是任务状态机。不要生成历史审计表、复杂阶段状态或 Git Diff 报告，除非用户本身要求这些内容。

## 模板沉淀

用户确认一次任务沟通有效，并要求保存为模板时，将具体业务内容变量化，只生成可复用文本，不创建模板市场或云端数据。

常用变量：

- 页面名称：`{{page}}`
- 代码路径：`{{files}}`
- 问题现象：`{{symptom}}`
- 任务目标：`{{goal}}`
- 限制要求：`{{constraints}}`
- 期望结果：`{{expected_result}}`

模板结果包含：模板名称、适用场景、固定规则、可变参数和一个使用示例。只变量化会随任务变化的内容，证据要求、禁止编造、修改边界等稳定规则保留为固定文本。
