# 智能追问规则

先识别已经确认的信息，再判断缺口是否会改变生成结果。以下内容是决策提示，不是固定问卷；每次最多选择三个最关键的问题。

用户只给出“做一个弹窗”“新增登录页”“修复支付报错”等简短但具体的任务，不等于要求空白模板。只要仍有会改变实现方向的关键缺口，就先展示可选择问题，等待用户选择后再生成话术。只有用户明确说“空白模板”“先生成”或“按默认处理”时，才跳过追问。

## 提问形式

- 优先调用环境提供的结构化用户输入工具（如 `request_user_input`）发起一轮可点击单选题；工具不可用时，在聊天正文中使用简短的编号问题和互斥选项降级追问。
- 每题只包含一个决策点，提供 2–3 个互斥选项；将风险最低或最常见的选项放在第一项，并在标签中标记“推荐”。
- 为每个选项写一句简短说明，明确它会怎样影响实现范围、交互结果或验收方式。
- 使用结构化工具时不要手动添加“其他”选项；客户端会自动附加自由输入入口。使用文本追问时，直接说明用户可以补充未覆盖的答案，不要为了自由输入额外编造选项。
- 工具在当前模式不可用时，不要要求用户切换模式。改用同一轮文本追问，每题使用编号，选项使用简短标签并附一句影响说明；允许用户回复选项名称或自然语言答案，不要强制使用 `1A、2C` 等编码格式。
- 不要把“待补充”包装成选项，也不要为了凑满选项而编造业务规则。
- 优先把可枚举的缺口转成单选题。具体文案、精确路径等无法合理枚举的答案，可以通过客户端自动提供的“其他”入口由用户填写。

## 通用判定

必须优先确认：

- 用户只要求分析还是允许修改。这会改变执行权限时必须确认；用户已经说“定位”“修复”“实现”时不要重复询问。
- 目标或预期结果存在多个合理解释，且不同解释会产生不同实现时必须确认。
- 修改范围、兼容要求或禁止事项会显著影响方案，但当前信息无法从仓库确认时必须确认。

不要询问：

- 能从仓库、设计稿、接口文档、日志或当前对话读取的信息。
- 不影响第一版方案的偏好、背景故事或可在执行中安全确认的细节。
- 用户已经明确回答过的问题。

问题应包含具体上下文和互斥方向。例如：“你希望这次只定位根因，还是确认根因后允许直接修复？”不要问“你还有什么要求？”

## 新需求开发

按需确认：

- 功能服务于哪个用户动作或页面流程。
- 核心触发条件、交互结果或数据来源存在多个实现方向。
- 必须兼容的端、状态或旧行为。
- 验收标准无法从需求或设计稿判断。
- 代码放置位置存在多个会改变复用范围或组件边界的合理方案，并且无法通过仓库结构判断。

示例：

- “这个弹窗由进入页面自动触发，还是由用户点击按钮触发？”
- “确认按钮只关闭弹窗，还是还要提交数据或跳转页面？”
- “没有设计稿时，是复用项目现有弹窗样式，还是需要新增视觉样式？”

追问示例（结构化工具和文本降级共用相同问题与选项）：

- 问题“这个弹窗如何触发？”可提供“点击按钮触发（推荐）”“进入页面自动触发”“满足业务条件时触发”。
- 问题“确认按钮执行什么操作？”可提供“仅关闭弹窗（推荐）”“提交数据后关闭”“跳转到其他页面”。
- 问题“弹窗使用哪种视觉方案？”可提供“复用现有样式（推荐）”“按设计稿实现”“新增视觉样式”。
- 每个选项还需说明对应影响；不要额外创建“其他”，由客户端自动展示。

### 弹窗类需求

用户只说“帮我生成弹窗”时，不要立即输出包含一组“待补充”的话术。先从下面方向中选出最多三个最影响实现的问题，并用当前可用的追问形式展示：

- 问题“弹窗代码放在哪里？”可提供“按现有项目结构判断（推荐）”“写在当前页面中”“拆成独立复用组件”。只有无法读取仓库或现有结构不能唯一确定时才询问。
- 问题“这个弹窗如何触发？”可提供“用户点击后触发（推荐）”“进入页面自动触发”“满足业务条件时触发”。
- 问题“确认按钮执行什么操作？”可提供“仅关闭弹窗（推荐）”“提交数据后关闭”“跳转到其他页面”。
- 问题“这个弹窗属于哪种内容？”可提供“信息提示（推荐）”“二次确认”“表单填写”。具体标题和正文可让用户通过“其他”入口填写，或在不影响方向时保留为待确认项。

每题选项必须附带一句影响说明。例如“拆成独立复用组件”应说明会新增组件文件并适用于多处调用。用户回答后，将选择结果写入最终话术，不要继续保留对应字段为“待补充”。

## Bug 定位

按需确认：

- 只定位原因，还是确认根因后允许修复。
- 问题能否稳定复现，以及最短复现步骤。
- 预期结果和实际结果是否明确。
- 最近变更、日志或请求样本是否直接关系到候选原因。

示例：

- “这个问题能稳定复现吗？如果能，请提供最短操作步骤。”
- “你希望这次只定位根因，还是确认根因后允许直接修复？”
- “问题出现前是否修改过请求拦截器、接口封装或登录状态逻辑？”

不要因为缺少日志就阻塞生成定位话术；只有日志内容会决定排查分支时才询问。

## UI 还原与走查

按需确认：

- 只输出差异清单，还是允许修复已确认差异。
- 目标页面、设计稿版本、设备尺寸或页面状态不明确。
- 设计稿与现有业务行为冲突时以哪一方为准。

示例：

- “这次只需要走查并列出差异，还是允许直接修复确认后的视觉问题？”
- “需要以哪个设备尺寸和页面状态作为主要验收基准？”

## 代码清理

按需确认：

- 清理范围或目标不明确。
- 是否必须完全保持公开接口、运行行为和兼容性。
- 删除候选内容可能被动态引用，且无法通过代码检索证明安全。

示例：

- “本次只清理指定文件，还是允许同步调整它们的直接调用方？”
- “是否要求对外接口和运行行为完全不变？”

## 接口联调

按需确认：

- 目标是核对契约、定位异常，还是直接完成适配。
- 缺少权威接口契约，且字段结构会决定实现方向。
- 联调环境、鉴权方式或实际响应样本决定问题能否复现。

示例：

- “这次需要先核对接口差异，还是允许按正式契约直接修改前端适配？”
- “哪份 OpenAPI 或接口文档是当前联调的权威版本？”

缺少正式契约且用户无法提供时，不编造字段；生成以收集实际请求和响应证据为目标的话术。
