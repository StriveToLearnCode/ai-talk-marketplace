# 智能追问与默认规则

追问的目的只是避免 AI 在关键方向上猜测，不是让用户填写需求表单。

## 何时追问

只有答案不同会改变以下内容时才追问：

- 对任务目标或问题现象的理解
- 只分析、先给方案或直接执行的方向
- 允许修改的代码范围
- 关键业务结果或兼容边界
- 最终验收方式

默认只问一个最影响方向的问题。只有多个相互独立的答案都会改变目标、权限或验收时，才允许一轮询问两到三个问题；每轮绝不超过三个。场景已经明确时不要再问用户选择模板。

## 先读取再提问

优先从当前对话、`AGENTS.md`、`README.md`、`package.json`、目录结构、Git 状态、用户提到的文件、相关组件和工具函数中确认信息。

不要询问能够读取到的技术栈、包管理器、启动命令、测试命令、文件位置或已有组件。不得把没有读取到的信息写成项目事实。

## 提问方式

- 每题只问一个会影响方向的决策点，并结合用户当前任务具体表述。
- 能列出主要方向时，提供 2–3 个互斥选项和一句影响说明；环境支持结构化输入工具时可优先使用。
- 无法枚举的复现步骤、文案或业务规则，用一个自然语言问题询问，不为凑选项编造答案。
- 说明用户可以暂不回答，以及未回答时采用的默认方向。
- 用户说“先生成”“按默认处理”或拒绝回答时，立即停止追问。

正确示例：

```text
还缺少一个会影响定位方向的信息：

这个问题通常发生在首次进入页面、返回页面，还是连续操作以后？

如果暂时不清楚，我会默认先从生命周期、定时器和数据更新逻辑排查，并把触发条件标为未确认。
```

避免：

```text
请填写技术栈、项目名称、文件路径、启动命令、测试命令和完整验收标准。
```

## 默认处理

- 执行意图不明确：默认“先给方案”。
- 修改范围不明确：限定为用户提到的页面、模块及其直接依赖，不授权无关重构。
- 验收方式不明确：要求使用项目已有验证能力，并列出仍需人工确认的结果；不要替 Plan 模式展开完整测试计划。
- 资料缺失但不影响任务方向：直接生成话术，将资料标为“未提供”或“未确认”。
- 多种解释都会造成明显不同结果：只问最关键的一个问题，不自行选择高风险方向。

## 场景提示

- Bug：优先确认实际现象、触发条件、预期结果和是否允许修改；缺日志不应自动阻塞话术生成。
- 新需求：优先确认核心用户结果、关键交互和明确不做的内容；可从项目判断的组件复用不询问用户。
- UI：优先确认对照来源、目标页面/状态和验收尺寸；不要询问设计稿中已经可见的信息。
- 接口：优先确认权威契约和联调目标；没有契约时要求收集真实请求/响应，不编造字段。
- 审查：优先确认审查范围；默认只审查不修改。
- 清理：优先确认行为兼容边界和范围；无法证明安全的删除只报告。
- 测试：优先确认要保护的行为或回归；测试框架和命令从项目读取。
- 方案讨论：优先确认决策目标和硬约束；不提前拆成实施任务。
