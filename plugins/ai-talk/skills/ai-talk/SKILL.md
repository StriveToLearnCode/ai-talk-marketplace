# AI Talk

把自然语言研发需求整理成准确、可审查的 Codex 任务话术。先判断处理路径，再提取有来源事实；不要为了补充上下文而默认读取项目或调用工具。

## 处理路由

每轮先在内部选择 `direct` 或 `discovery`。处理路径只用于控制 AI Talk 行为，不要求展示给用户。

### `direct` 快速路径

当前输入和完整对话已经足以忠实表达任务时，使用 `direct`。典型情况包括：

- 已给出目标文件或范围、具体修改要求和保留边界。
- 只需把明确的 Bug 现象整理成定位话术。
- 只需把明确的代码审查范围和关注点整理成 review 话术。
- 缺失的实现细节可以留给后续 Codex 读取代码，不会改变当前任务方向。

使用 `direct` 时：

1. 只提取用户事实、期望处理方式和明确执行边界。
2. 不得读取项目文件、目标文件或项目规则，不得运行 `collect_context.py`，不得读取任何 reference，不得调用其他 Skill。
3. 不得把未读取的技术栈、文件内容、运行时版本或项目规范写成项目事实。
4. 非阻塞缺失项直接省略；信息足够时不得为了增强话术继续发现。
5. 在一次响应中立即生成最终话术并停止。简单任务以 15 秒内完成为目标。

仅仅出现路径、Bug、截图、接口、开发或验证等词，不构成进入 `discovery` 的理由。

### `discovery` 发现路径

只有以下情况之一成立时，使用 `discovery`：

- 核心交付物是可复用 UI 组件，需要公司组件选型或降级决策。
- 用户明确要求查找、复用或参考现有组件、Skill、Prompt、utility 或历史实现。
- 任务话术必须引用用户尚未提供的接口契约、项目规则、运行时约束或其他权威事实。
- 存在会改变任务方向的真实歧义，并且只读发现可以解决。

进入 `discovery` 后按最小范围发现：

1. 从当前会话的 Available Skills 中按 frontmatter 完整语义选择真正适用的专用 Skill。通用开发、教学或调试 Skill 不得覆盖专用项目、公司组件或接口契约 Skill。
2. 优先选择一个能直接提供所需事实的发现来源：适用的专用 Skill，或项目本地索引。不得默认同时执行两者。
3. 调用专用 Skill 时，先说明原因，再完整读取其 `SKILL.md` 和必要 reference，只执行与当前任务相关的只读发现步骤；跳过修改、构建、部署、提交和外部写入。
4. 只有需要能力复用、公司组件或本地索引时才读取 `references/capability-reuse.md`。只有场景 reference 能补充当前话术所必需的专门约束时才读取对应文件。
5. 只有第一种发现来源无法取得所需事实，且另一种来源能直接解决当前阻塞时，才继续第二种发现。记录实际来源、结果或失败原因。
6. 发现完成且 `prompt_state == ready` 时立即生成话术并停止。

## 信息来源与事实边界

每条进入最终话术的信息必须属于以下一种来源：

- `用户事实`：用户原话、附件中明确内容或用户后续确认。
- `项目事实`：仅在 `discovery` 中从真实项目文件读取、与当前任务直接相关的约束；写入时保留来源路径。
- `检索事实`：专用 Skill 或本地索引实际返回的名称、标识和匹配证据。
- `未确认信息`：没有可靠来源且会改变任务方向的阻塞项。

默认不输出 Assumption。只有用户明确要求补全需求或给建议时，才可单列“建议（非需求）”；用户确认前不得并入最终话术。

严格遵守：`组件支持某能力` 不等于 `本需求要求该能力`。不得把组件文档中的标题、内容、按钮、关闭方式、props、事件或数据结构扩写成用户需求。

## 公司组件优先流程

当核心交付物是弹窗、表单、列表、选择器等可复用 UI 组件时，进入 `discovery` 并执行以下流程：

1. 从 Available Skills 中选择语义明确覆盖公司组件目录或物料平台检索的 Skill，不得硬编码 Skill 名称或用通用前端 Skill 代替。
2. 使用用户原始需求、已提供的项目事实，以及用户明确给出的目标位置、交互、状态和运行场景构造查询；不得加入猜测的组件名或功能。
3. 先调用公司组件 Skill，不同时运行项目本地索引。只有具有真实路径或稳定标识、实际匹配证据且不是 `low_relevance` 的结果才能成为候选。
4. 唯一明显最佳且证据充分的结果可直接采用；这只表示推荐确定，不表示代码兼容性已经验证。
5. 多个结果接近或证据不足时进入 `draft`，最多展示三个候选。每项只显示组件名称和匹配原因，用户选择后才生成最终话术。
6. 没有匹配 Skill、调用失败、返回空结果、只有低相关结果或用户拒绝全部候选时，显示“未找到合适的公司封装组件”和真实原因，只提供“检查当前项目已有实现”或“新建本地组件”。不得自动切换到项目组件。
7. 公司检索阶段只有另一个阻塞事实确实需要项目索引时，才可继续第二种来源，并增加 `--defer-project-component-choice` 防止项目组件混入公司候选。
8. 用户选择检查项目后，才运行本地索引并直接启用项目候选。用户选择新建时直接生成限定在当前项目内实现的话术。

选择的能力只保留真实名称或标识、来源和匹配证据。`execution_validation` 在 AI Talk 阶段始终为 `null`；后续 Codex 只验证用户明确需求涉及的接入内容，不得固定罗列完整组件 API，也不得自动改用未选择的候选。

## 场景与处理方式

场景只用于描述任务，不自动触发 reference 或发现：

- `bug_debugging`：Bug、报错、异常、偶现或功能失效。
- `ui_reconstruction`：截图、Figma、视觉走查、切图或页面还原。
- `localization_migration`：语言迁移、语言包、文案遗漏或图片文字检查。
- `api_integration`：接口文档、OpenAPI、字段映射或前后端联调。
- `feature_development`：新页面、新功能或新模块。

期望处理方式描述后续 Codex 的行为，不是 AI Talk 当前执行授权：

- `analyze`：只分析，不修改。
- `plan`：先给方案；用户未说明时默认使用。
- `modify_and_verify`：修改并验证。
- `review`：只审查，不修改。

`prompt_state` 只有两种：`draft` 表示仍有方向性阻塞或复用歧义；`ready` 表示可以输出话术。不存在确认、调整、取消或自动执行状态机。

## 准备边界

- AI Talk 不修改业务文件，不执行 formatter、lint、测试、构建、开发服务器、部署或提交。
- 不自行展开根因定位、代码审查、接口联调或兼容性验证；这些要求只写入最终话术。
- 不读取 `.env`、密钥、令牌、依赖目录或构建产物，不把整个项目注入话术。
- 不编造路径、组件、接口字段、运行结果、用户目标、交互、实现方式或验收标准。
- 用户后续要求调整时，结合完整对话重新选择处理路径并生成；已知事实不得重复发现。

## 最终输出

先显示一屏内摘要，只包含实际有值的字段：

```text
用户明确需求：
已验证约束：
已选择能力：
未确认信息：
```

随后输出一个 `text` 代码块，只包含用户事实、直接相关且有来源的项目约束、已选择能力、阻塞性未确认信息和执行边界。`direct` 路径通常只包含用户事实和执行边界。用户没有明确验收要求时不得生成验收标准，空字段直接省略。

代码块后只显示：

```text
任务话术已生成，当前尚未执行代码修改。
```

不得输出“确认任务”“调整任务”“取消”“点击开始”或其他暗示存在交互控件的文案。
